# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

NetSpaceWar: a multiplayer UDP network clone of Spacewar!, written in C. Git repo (GitHub `josephcolton/NetSpaceWar`). It was migrated from an old SVN checkout at `/opt/netspacewar-code` (SourceForge, revision 128), which is no longer edited. Sources are in `src/`, with `CMakeLists.txt` at the root.

**Commit only to `main`.** Don't create branches; the owner wants all history on `main` for simplicity.

## Build

```sh
cmake -S . -B build
cmake --build build                          # all targets
cmake --build build --target SpaceWarAI      # one target
cmake -S . -B build -DNSW_BUILD_CLIENT=OFF   # server + AI only
```

- `SpaceWarServer` and `SpaceWarAI` need nothing beyond libm. The AI is headless and does not link `gui.c`.
- `NetSpaceWar` (the game: menus + client) uses **SDL3**. CMake uses an installed SDL3 if found; otherwise it FetchContent-downloads the pinned release and links it statically (`NSW_FETCH_SDL`, default ON). On Linux, SDL's own configure step fails unless X11 or Wayland dev headers are installed (README lists them).
- **Headless testing** (no display, no X11 headers): configure a separate tree with `-DSDL_UNIX_CONSOLE_BUILD=ON` (e.g. `build-headless/`) and run the client with `SDL_VIDEODRIVER=offscreen`. SIGTERM/window-close becomes `SDL_EVENT_QUIT`, which logs out cleanly.
- `OS_<CMAKE_SYSTEM_NAME>` (e.g. `OS_Linux`) is defined for the `#ifdef` blocks in the clients.
- **Windows**: `cmake/mingw-w64-x86_64.cmake` cross-compiles from Linux (needs `x86_64-w64-mingw32-*` on PATH, from distro `mingw-w64` or llvm-mingw). The same toolchain file also works natively with Strawberry (`build-windows/`); it falls back to plain `windres` because Strawberry has no prefixed one. Builds are static, so the `.exe` files need only system DLLs.
- **Native Windows** (Strawberry Perl's MinGW gcc 13 + Ninja): `cmake -S . -B build-win -G Ninja -DCMAKE_C_COMPILER=gcc` with `C:\Strawberry\c\bin` first on PATH (ahead of `C:\msys64`). Verified working: server + bots, the game client, the launcher's host flow (spawns and kills server/bots), and window-close logout. The first time a host listens on 0.0.0.0, Windows Firewall asks about `SpaceWarServer.exe`.
- **Windows installer**: see Releasing below.
- Globals live in the `.c` files and are declared `extern` in the headers. Keep it that way: defining them in headers breaks the link under GCC ≥ 10 (`-fno-common`).
- There are no tests or linters. To smoke-test, run `./SpaceWarServer localhost <port>` and two `./SpaceWarAI localhost <port> botN` from `build/`. The server prints joins, leaves, deaths and respawns; add `--verbose` to see every packet (roughly 20 player/missile updates per second per client). The bots and game print only status and errors; set `DEBUG` to 1 in `global.h` to have them print every packet.

## Releasing

Releases are Windows installers published as GitHub releases (`josephcolton/NetSpaceWar`). The README's Download section links to `/releases/latest`, so it needs no edit per release.

Released so far:
- `v1.0.0`: first release, with the installer and icon.
- `v1.1.0` (tag on `8d9645b`): the version check and About screen, volcanoes and recharge orbs, asteroids, radar wrapping, and `DEBUG` off. It can't play with 1.0.0. 1.0.0 clients are refused without an explanation, because they predate the check.

`main` may be ahead of the latest release: the owner pushes updates without releasing, and bumps `project(VERSION)` for them anyway, so `main` is currently 1.2.0 (in progress: safe spawns, kill messages, match length, settings screens, sound and music, gamepad, LAN server search) with no release after 1.1.0. Players can play together when the first two numbers match (see Version check). So bump the minor version (1.2.0) for anything that changes the protocol, since a protocol change must not reach players who could still connect, and also for new gameplay. Bump the patch version (1.1.x) for fixes that keep the protocol.

1. Bump `project(VERSION ...)` in `CMakeLists.txt` and commit on `main`. A new major or minor version can't play with older ones (see Version check).
2. `cmake --workflow --preset windows-release` (`CMakePresets.json`, Strawberry's `C:\Strawberry\c\bin` first on PATH) configures, builds and runs CPack's `INNOSETUP` generator in `build-release/`, producing `build-release/NetSpaceWar-<version>-setup.exe`.
3. Tag and publish: `git tag -a vX.Y.Z -m "NetSpaceWar X.Y.Z"`, `git push origin vX.Y.Z`, then `gh release create vX.Y.Z build-release/NetSpaceWar-X.Y.Z-setup.exe --title "NetSpaceWar X.Y.Z" --notes-file <notes> --verify-tag`. Releases are normal (not pre-release); the owner makes a follow-up release if something is wrong. Before tagging:
   - check that the `build-release/` exes need only Windows DLLs (`objdump -p`) and that `NetSpaceWar.exe`'s file version matches,
   - run the release server and two bots briefly,
   - then confirm the uploaded asset's size matches the local file and `/releases/latest` redirects to the new tag.

   Release notes have three parts: install (including the SmartScreen "More info, Run anyway" step and the version rule), what's new for players, and "Requires 64-bit Windows 10 or later".

Tools on this machine: Inno Setup 6 is installed per-user in `%LOCALAPPDATA%\Programs\Inno Setup 6`, where `find_program(NSW_ISCC)` finds it. The GitHub CLI is a portable copy at `%LOCALAPPDATA%\Programs\GitHub CLI\bin\gh.exe` and is **not on PATH**, so call it by full path. It is logged in as `josephcolton`. winget is broken here (source error 0x8a15000f), so download tools directly from their official releases instead.

Installer details:
- The version from `project(VERSION)` also goes into `res/netspacewar.rc.in`, the icon and version resource linked into `NetSpaceWar.exe`. SDL uses the exe's first icon for the window.
- Installer extras (the firewall rule task and its removal on uninstall, plus finish-page text explaining taskbar pinning, which installers can't do) are in `res/installer.iss`, which CPack `#include`s at the top of its generated script. The other installer settings are the `CPACK_*` variables at the end of `CMakeLists.txt`.
- Never change `CPACK_INNOSETUP_SETUP_AppId`, because upgrades depend on it.
- `res/make_icon.py` (standard library only) regenerates `res/netspacewar.ico` and `.png`.
- The installer isn't code-signed; the owner accepts the SmartScreen "Run anyway" step.
- The generated script is `build-release/_CPack_Packages/win64/INNOSETUP/ISScript.iss`. Run `ISCC` on it directly to see compiler warnings, which CPack hides.

## Run

```sh
# from build/
./NetSpaceWar                                   # menu: host (spawns server + bots) or join
./NetSpaceWar    <hostname> <port> <username>   # join directly
./SpaceWarServer <address> <port> [--verbose|--silent] [--planets N --gravity N ...]  # 0.0.0.0 = all interfaces; no args lists options
./SpaceWarAI     <hostname> <port> <username>
```

Client keys: arrows turn/thrust, Space or Left Ctrl fires, Tab hyperjumps, Z/X move energy between weapons and shields, Esc quits.

## Architecture

**Authoritative server, thin clients, over UDP.** The server owns all game state and physics. Clients send input actions and render whatever the server broadcasts.

- **Platform layer** (`platform.h`/`platform.c`): all OS differences live here, namely the socket headers, `netInitialize()` (WSAStartup), `netLastError()`, `netIgnoreConnReset()` (turns off Windows' UDP connection-reset errors), and `platformNow()` (a monotonic clock). Other files include it via `global.h`; don't add POSIX-only headers or calls (`bzero`, `gettimeofday`, `errno` for socket errors) elsewhere. Sockets are stored as `int`, even on Windows. `sendto` buffers are cast to `(const char *)` for Winsock.
- **Protocol** (`global.h`): every packet is a `packed` struct whose first field is `message_t mtype` (`MSG_*` constants). Receivers cast the raw buffer to `struct msg_basic` to dispatch, then cast to the specific `msg_*` struct. Variable-length messages (`msg_updateplayers`, `msg_updatemissiles`, `msg_updateorbs`, `msg_updateasteroids`, `msg_staticobjs`, `msg_clientlist`) carry `obj_count` plus a trailing zero-length array of `dataNode*` structs, and are received into `MAX_PACKET` (64 KB) buffers, since a full missile list is about 2.6 KB. Wire structs use fixed-width types inside `#pragma pack(push, 1)`, and `_Static_assert`s at the end of `global.h` pin their sizes. Update the asserts deliberately when changing the protocol. `msg_clientlist` sends `struct wireClient`, not the in-memory `dataNodeClients`. Client handlers clamp `obj_count` to the `MAX_COUNT_*` limits, and receivers drop packets shorter than a `message_t`. The client sends input as `msg_clientupdate` with an `ACTION_*` code and generic `var1/var2/var3` fields; their meaning depends on the action (for THRUST, var1 = accel and var2 = angle delta; for TRANSPWR, var3 = energy). All tuning constants and capacity limits (`MAX_COUNT_*`) are also in `global.h`.
- **Game options** (`options.h`/`options.c`, linked into all three programs): one table of host-configurable rules (name, label, help, default from `global.h`, min/max/step). The server reads `--name value` flags into `serverOptions[]` (in `sdata.c`) and game code reads them with `SERVER_OPTION(GRAVITY)` etc., never the `global.h` default. The launcher's Game Settings screen (from Host) builds a picker per table row, saves them in `settings.txt` under the same names, and passes all of them as flags when it spawns the server. Adding a rule means adding an `OPTION_*` enum value and a table row, then using `SERVER_OPTION()` on the server. Clients learn the rules from `msg_gameoptions` (`obj_count` + `int32_t` values in enum order, so new options must go on the end of the enum): they request `DATA_OPTIONS` after login and `clientRetryLogin()` repeats the request until it arrives. They are kept in `cdataOptions[]` (defaults until then, `cdataOptionsReceived` flags arrival) and read with `CLIENT_OPTION(x)`. The AI derives its cruise speed, fire and engage ranges, planet margin and shot-energy check from them (`aiCruiseSpeed()` etc. in `ai.c`); the GUI lists them under the scoreboard. The client's missile timeout is `CLIENT_MISSILE_STALE`, refreshed on each update, so it doesn't depend on the server's missile life.
- **Volcanoes and recharge orbs** (`physics.c`, the section before `physicsUpdate()`): `volcanoInitialize()` (called by `serverInitialize()` after the planets exist) sets `volcano` on `SERVER_OPTION(VOLCANOES)` random planets. `volcanoUpdate()` runs after the other collisions. It handles ship pickups (full energy and shields, skipped for ships already below zero this tick) and planet hits (any planet, including the source), counts down each orb's `life` (`ORB_LIFE`), and erupts each volcano whose `volcanoWait` (indexed like `sdataArrayPlanets`) has run out while it has no orb out. Removing an orb restarts its source's wait (`ORB_WAIT` option). Launch speed is a random 0.9-1.1x the speed needed to escape the planet's 1/r gravity out to `GRAVITY_RANGE`, so about 40% escape and the rest fall back after 7-11 s at default gravity. Planets pull on orbs; missiles pass through them. The server sends the whole orb list every tick in `msg_updateorbs`, even when it's empty, and the client replaces `cdataOrbs[]` with it, so orbs need no delete message. The planet's `volcano` flag is on the wire in `msg_staticobjs`, and the client's handler updates planets it already has, so the server can resend the list when a planet changes. `gameOptionsFix()` keeps volcanoes <= planets in the launcher; the server rejects that combination on the command line.
- **Asteroids** (`asteroids.c`, server only): `asteroidsUpdate()` runs after `volcanoUpdate()` and before `deadShipDetect()`. It spawns an asteroid every `ASTEROID_INTERVALS[level]` s (+-25%) while anyone is playing, at a spot outside every ship's view (`VIEW_HALF_W/H`) and clear of planets, aimed roughly at a random ship. Asteroids drift straight (no gravity on them), and after `ASTEROID_TRIP` units they leave, but only while unseen. Planets destroy them, with `ASTEROID_TOGGLE_CHANCE` of `volcanoToggle()`, which resends the planet list. They destroy orbs. Missiles do `MISSILE_DMG` (`POINTS_ASTEROID_HIT`/`_KILL` to the owner). Ramming is in `asteroidRam()`: both take `CRASH_DMG`*5, the ship's velocity relative to the asteroid is reflected, the ship is moved clear, and a destroying ram scores the kill. `asteroidGravity()` adds an `ASTEROID_GRAVITY` fraction pull within `ASTEROID_GRAVITY_RANGE` to ships, missiles and orbs in `physicsUpdateGravity()`. Like orbs, the full list goes out every tick (`msg_updateasteroids`) and replaces `cdataAsteroids[]`. The client draws each asteroid's shape and spin from its objectID, with one crack per 25 HP lost. The planet list is also resent every `STATICOBJS_TICKS`, and the client's staticobjs handler stamps `cdataPlanetChanged[]` when a volcano flag flips, which drives `gui_draw_volcano_change()`. The Asteroids option is a level with `names` in the options table: `gameOptionText()` shows the name everywhere, and the server's command line takes either the name or the number. Ramming was tested with a scratch program linking the server sources and calling `physicsUpdate()` directly. Do that again for collision changes, since bots avoid asteroids.
- **Naming convention**: `shandle_msg_*` / `ssend_msg_*` (server, `server.c`) and `chandle_msg_*` / `csend_msg_*` (client, `client.c`). Adding a message means adding a `MSG_*` constant, a struct in `global.h`, a send/handle pair, and an `if (mtype == …)` line in the dispatcher: `handle_socket()` in `SpaceWarServer.c`, or `clientReceive()` in `client.c` (shared by the game and the AI).
- **Server loop** (`SpaceWarServer.c`): `select()` on one UDP socket, with a timeout of `SERVER_TIMEOUT` (tick = `PHYS_SECS_PER_UPDATE`, 50 ms). `lastTimeLeft()` in `sdata.c` subtracts time spent handling packets, and the timeout branch resets `lastTime` so each tick is timed from when it fired. On each tick it runs `checkClientKeepAlive()`, `sdataUpdateAll()`, `physicsUpdate()` (positions, gravity, collisions, volcanoes, asteroids, shield restore, and scoring in `physics.c`/`asteroids.c`), then `broadcastUpdatePlayers/Missiles/Orbs/Asteroids()` and `broadcastStaticObjsRepeat()`. Clients are identified by their source `sockaddr_in`.
- **State stores**: `sdata.c` (server) and `cdata.c` (client) mirror each other. Each keeps a fixed-size array of pointers per object type (`*ArrayClients/Ships/Missiles/Planets/Explosions`) plus a count, with Create/Delete/Update/Lookup-by-`objectID` functions. Object IDs come from `sdataNewObjectID()`. Space is a torus from -100 to 100 on both axes (`xcoordLoop`/`ycoordLoop`).
- **Hosted servers shut themselves down** (`--host-player NAME`, `server.c`/`SpaceWarServer.c`): `serverClientLeaving()` runs before a client is deleted, both on logout and on keepalive timeout. When the host leaves, it sets `serverShutdown`, which ends the main loop. So does the host not having joined after `HOST_JOIN_TIMEOUT` (30 s). On the way out the server sends `msg_logoutack` to everyone left. Clients show that as "The server ended the game", and bots exit at once. If the host's game crashes, the server goes after the 15 s keepalive timeout, so it can't outlive the game. Standalone servers (no flag) are unchanged.
- **Version check**: CMake passes `project(VERSION)` to every program as `NSW_VERSION`. `msg_login` and `msg_loginack` both carry it. `versionCompatible()` (`global.h`) requires the same major and minor version (`versionSeries()`), so patch versions play together. The server refuses an incompatible client with `STATUS_VERSION`, naming its own version, and logs who tried. A client that an old server lets in (one that doesn't check) logs straight back out. 1.0.0 sent no version field, so an empty one (receive buffers are zeroed) never matches and is shown as `VERSION_OLDEST`. 1.1.0 itself compares the whole string, so a 1.1.0 client refuses a 1.1.x server. The launcher's About screen shows the version.
- **Client connection** (`client.c`, bottom): `clientOpenSocket()`, `clientReceive()` (reads and dispatches one packet and returns its type), `clientRetryLogin()` (resends `MSG_LOGIN` every `LOGIN_RETRY` s until acked; the server re-acks a repeat login from the same address), and `clientConnectionProblem()` (gives up after `CONNECT_TIMEOUT` with no login, or after `SERVER_SILENCE` with no packets). Failures put a player-facing reason in `clientStatusMessage`. `cdataInitialize()` frees the previous game's objects, so it is safe to call before each game.
- **Game** (`game.c`): `gamePlay(host, port, name)` runs one game in the shared window and returns `GAME_LEFT` (Escape), `GAME_CLOSED` (window closed), or `GAME_FAILED`. `gui_get_input()` runs every pass, even while connecting, so the window stays responsive.
- **Launcher** (`launcher.c`, entry from `NetSpaceWar.c` when there are no args): a menu state machine (main / host / join / settings / about screens of `LauncherItem`s: buttons, text fields, a number choice) with keyboard and mouse input, drawn with `SDL_RenderDebugText` through `gui_text*()`. Hosting spawns `SpaceWarServer 0.0.0.0 <port> --silent --host-player <name>` (plus every game option) and N `SpaceWarAI 127.0.0.1 <port> "Bot N"` from `SDL_GetBasePath()` via `SDL_CreateProcessWithProperties`, then calls `gamePlay`, then force-kills them. On Windows they start as background processes (no console window); on POSIX they are normal children with stdio sent to null, so they share the terminal's Ctrl+C. Settings persist in `SDL_GetPrefPath("NetSpaceWar","NetSpaceWar")/settings.txt`. When testing headless, set `XDG_DATA_HOME` to keep that file out of `$HOME`.
- **GUI** (`gui.c`): draws at a 640x480 logical size (`GUI_SCREEN_W/H`) that SDL letterboxes into the resizable window. The game drawing code still uses the original Allegro-style calls (`gui_line`, `gui_circle`, `gui_putpixel`, `gui_makecol`…), implemented as small SDL wrappers at the top of the file over a `GuiArea` (a rectangle of the window, used for the main view and the radar). Menu helpers (`gui_text*`, `gui_draw_backdrop`, `gui_draw_status`) are at the bottom. During a game `SDL_PollEvent` runs only in `gui_get_input()`; the launcher polls events itself. Escape sets `P_GUI_FLAG_QUIT` (leave the game) and closing the window sets `P_GUI_FLAG_CLOSE`. The `UGLY_MISSILE_DRAW_POS_FIX` flag redraws only after both a players packet and a missiles packet have arrived.
- **AI** (`SpaceWarAI.c` + `ai.c`): the same connection helpers without a GUI. It links `client.c`/`cdata.c`/`options.c` but not `gui.c`, and exits when the server goes quiet. `clientAIupdate()` runs once per `MSG_UPDATEPLAYERS` (not every loop pass), so it always acts on fresh state. It works by choosing a wanted velocity (close in, hold position, head for a recharge orb when energy + shields is below `AI_RECHARGE_BELOW`, or flee a planet or asteroid using a course lookahead, which wins). With no ship in firing range it shoots the nearest asteroid (`aiLeadAngle()`) and thrusting along the difference; otherwise it turns to a lead-intercept angle and fires. It deliberately limits itself to the human client's `P_GUI_*` turn/accel/fire rates, because the server doesn't enforce them. Tuning constants (`AI_*`) are in `ai.h`.

## Notes

- **Scores** live on the server's `dataNodeClients` (`score`, `kills`, `deaths`). Ships and missile owners share the client's objectID, so `scoreAdd()`/`scoreCountKill()`/`scoreCountDeath()` look the client up by that ID and set `scoreChanged`. A killing missile awards `POINTS_KILL` and a non-fatal hit `POINTS_HIT`, in the missile collision code; every death (any cause) and its `POINTS_DIE` penalty are applied in `deadShipDetect()`. `broadcastScoreboard()` runs every tick and sends `msg_scoreboard` (`wireScore` entries that include usernames) when `scoreChanged` is set, or every `SCOREBOARD_TICKS`. Clients keep the latest copy in `cdataScores`; `gui.c` draws your score in the HUD and the full table while S is held or your ship is dead.
- **Event lines**: `serverEvent()` (log + broadcast) and `broadcastEvent()` (broadcast only) send `msg_event` text to every player. They carry deaths (`reportDeath()` in `physics.c`), joins and leaves. The client keeps the last `CLIENT_EVENTS` in `cdataEvents[]`, and `gui_draw_events()` shows them at the bottom for `GUI_EVENT_SHOW` s, fading out, yellow when they contain our name. They are cosmetic, so a lost packet is fine.
- Ships are placed by `serverSpawnPoint()` (`server.c`) when they join, respawn and hyperjump. It picks a random spot at least `SPAWN_PLANET_DISTANCE` from planet centers (inside their gravity is allowed), `SPAWN_ASTEROID_DISTANCE` from asteroids and `SPAWN_SHIP_DISTANCE` from other live ships. Planets are placed at least `PLANET_SPACING` apart. Both give up after 100 tries and use the last spot.
- `physicsUpdate()` must call `deadShipDetect()` last. If it runs first, ships sit at negative shields for a tick and a power transfer or shield restore can revive them.
- `DEBUG` in `global.h` is 0. Set it to 1 to make the clients print every packet they receive and the GUI's per-frame traces. Keep new client debug prints behind `if (DEBUG)`. The server instead uses `VERBOSE` (`server.h`), set by `--verbose`; `--silent` turns off its stdout entirely, and errors go to stderr. Game events go through `serverLog()` (timestamped, skipped when silent). Death messages come from `reportDeath()` in `physics.c`, which looks up what `noteHit()` recorded for that ship during the same tick. The launcher starts its server with `--silent`.
